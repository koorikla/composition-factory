### CF-344 (#232) — `P0` — YAML 1.1 keyword keys collapse under the Kubernetes decoder

The contract demanded the fix hold for "the full YAML 1.1 boolean and null token set
(`on/off/yes/no/y/n/true/false/null/~` and their case variants)", while the committed
test (`internal/emit/xrd_test.go:489` `TestXRDKeywordParametersAndRequired`) covers only
`on/off/yes/no` plus one nested object. The wider set was therefore probed end to end
through the built `cf` binary, not through the test.

Every name that validation **accepts** is emitted quoted, in both the `properties` key
position and the `required` list:

```
### key=on     25:              'on':      29:            required: ['on', providerName]
### key=Yes    25:              'Yes':     29:            required: ['Yes', providerName]
### key=OFF    25:              'OFF':     29:            required: ['OFF', providerName]
### key=Y      25:              'Y':       29:            required: ['Y', providerName]
### key=N      25:              'N':       29:            required: ['N', providerName]
### key=NO     25:              'NO':      29:            required: ['NO', providerName]
### key=ON     25:              'ON':      29:            required: ['ON', providerName]
### key=no     25:              'no':      29:            required: ['no', providerName]
### key=off    25:              'off':     29:            required: ['off', providerName]
### key=yes    27:              'yes':     29:            required: [providerName, 'yes']
### key=y      27:              'y':       29:            required: [providerName, 'y']
### key=n      25:              'n':       29:            required: ['n', providerName]
### key=No     25:              'No':      29:            required: ['No', providerName]
```

The names the emitter does **not** carry a quoting path for are refused at validation
instead, so no unquoted keyword reaches the document:

```
refused : 'null' -> spec.xrd.parameters.null: invalid parameter name (must be camelCase, ...)
refused : '~'    -> spec.xrd.parameters.~: invalid parameter name (must be camelCase, ...)
refused : 'True' -> spec.xrd.parameters.True: invalid parameter name (must be camelCase, ...)
refused : 'TRUE' -> spec.xrd.parameters.TRUE: invalid parameter name (must be camelCase, ...)
refused : 'Null' -> spec.xrd.parameters.Null: invalid parameter name (must be camelCase, ...)
```

The `EnvironmentConfig` `data` side — the third position the contract names — quotes the
key and leaves an ordinary key bare:

```
ACCEPTED: 'on'     | emitted:   'on': "alpha"
ACCEPTED: 'Y'      | emitted:   'Y': "alpha"
ACCEPTED: 'NO'     | emitted:   'NO': "alpha"
ACCEPTED: 'region' | emitted:   region: "alpha"
```

`internal/emit/yaml.go:64-79` is the mechanism: `yamlKeywords` carries the full token set
and `formatYAMLKey` lower-cases before lookup, so case variants are covered by
construction. **Verified clean, wider than its own test.**

### One observation this run could not resolve — deliberately not filed

On arrival the palette listed the 25 cached `s3.aws.m.upbound.io` kinds (`Bucket`,
`BucketACL`, …) alongside the native ones, taken from the seeded cache even though
`spec.sources` was `null`. After the `region` parameter was added and the document
written, a fresh load showed only the 16 native kinds, and `#lrail .kind[data-kind="Bucket"]`
was gone — including after typing `bucket` into `#psearch` (`count=0`).

Either state is defensible on its own: kinds following declared sources is the stricter
rule, and showing cached kinds on a blank canvas is the friendlier one. What a first-time
user actually gets is one then the other, with no event that explains the change. This
run could not establish which is intended, reproduce the transition twice, or name the
mechanism inside the cap, so **no issue was filed** — the evidence bar is not met.
Left here as the first thing for the next run with browser time to settle.
