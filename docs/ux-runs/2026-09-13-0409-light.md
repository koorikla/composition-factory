### CF-470 (#367) — essentials form, env repeater, expose-as-parameter — verified fixed

The headline defect was that a second env entry could not be added from the GUI. It can:
the inspector carries one `+ add variable` control, and clicking it twice writes both
indices.

```
after 1st add, env fields: ["spec.template.spec.containers[0].env[0].name"]
after 2nd add, env fields: ["spec.template.spec.containers[0].env[0].name","spec.template.spec.containers[0].env[1].name"]
```

Exposing a field as an XRD parameter carries the literal as a default and rewires the field:

```
params after:  "replicas": { "type": "integer", "required": false, "default": "2" }
spec.replicas field now: {"from":"params.replicas"}
```

The string-shaped `"2"` on an `integer` parameter is normalised at emit — the generated XRD
carries `default: 2` unquoted, so the type fidelity holds end to end and there is nothing to
file:

```yaml
              replicas:
                type: integer
                default: 2
```

An ESSENTIALS section is present on the Deployment with typed controls and six `↗ param`
expose actions.

The `+ add variable` repeater writes `name` keys only, so the emitted container carries
`env: [- name: 'VAR_1', - name: 'VAR_2']` with no `value` until one is typed. That is legal
Kubernetes (an omitted `value` defaults to `""`) and the brief scoped the repeater to add,
delete and renumber, so it is recorded as observed behaviour rather than filed.
