### M1 — First contact: an S3 bucket, from nothing

**Outcome: completed.** Blank start. The whole run — both missions, the close
verification, the gates and the spot-checks — took 18 minutes of wall clock
(07:29:46Z to 07:48:00Z), so per-mission timings below are step counts rather than
stopwatch readings; I did not instrument the driver for time-to-Generate and am not
going to invent a figure. M1 was 5 user-visible actions from blank canvas to a
generated Composition: close chooser, drag `Bucket`, `Wire`, `+ new XRD parameter…`,
Add.

Arrival puts the **starter-blueprint chooser** over the canvas as a modal. It is the
first thing a naive user meets and it is good: nine cards, each with a resource count and
an honest readiness badge — `● ready` for the S3 and SQS starters whose schemas are in
the seeded cache, `↓ 1 provider` / `↓ 2 providers` for the IAM and RDS ones that would
need a fetch. A user learns from the badge, before clicking, which starters cost a
download.

The one cost: it is a true modal, so the KINDS list is legible but inert beneath it. My
first drag attempt failed for exactly this reason and read as "drag does not work". A
person sees the dialog and closes it; a scripted driver does not. Recording it as
observation, not a finding.

With the chooser closed, dragging `Bucket` from KINDS onto the canvas worked on the
first attempt, and did more than drop a card: it added the provider to `spec.sources`
and scaffolded a default region.

```json
"sources":[{"provider":"ghcr.io/crossplane-contrib/provider-aws-s3:v2.7.0"}]
"resources":[{"name":"bucket","kind":"Bucket",...,"fields":{"region":{"value":"us-east-1"}}}]
```

Turning that literal into a parameter is the part I expected to hunt for and did not.
The Inspector's ESSENTIALS block puts `Val | Wire | Raw` on the region row; `Wire` opens
a `wire to…` dropdown whose last entry is `+ new XRD parameter…`, which opens an inline
name/type/required form. Naming it `region`, typing `string`, checking `req` and
pressing Add did both halves of the job at once — declared the parameter on the XRD and
bound the field to it:

```json
"parameters":{"providerName":{...},"region":{"type":"string","required":true}}
"fields":{"region":{"from":"params.region"}}
```

**Oracle met.** Generated Composition:

```yaml
          apiVersion: s3.aws.m.upbound.io/v1beta1
          kind: Bucket
          spec:
            forProvider:
              region: {{ $spec.region | quote }}
```

and the XRD declares it with its type and requiredness:

```yaml
              region:
                type: string
            required: [providerName, region]
```

No console errors at any phase.

### M2 — The status wire: IRSA

**Outcome: completed with a substitution.** 6 user-visible actions: search and drag
`ServiceAccount`, search and drag `Queue`, name the annotation and Add, `Wire`, pick
`resources.queue.status.atProvider.arn`, Generate.

The mission's IAM Role could not be built here. Adding the provider fails on the egress
policy, loudly and specifically:

```
{"error":"ghcr.io/crossplane-contrib/provider-aws-iam:v2.7.0: read image config: Get \"https://pkg-containers.githubusercontent.com/...\": Forbidden"}
HTTP 502
```

That is #68 (CF-183) and the seeded cache carries only `provider-aws-s3` and
`provider-aws-sqs`. **This is exactly where the missing schemas stop the mission.** I ran
the mission's mechanism with the cached SQS `Queue` standing in for the IAM Role and a
native `ServiceAccount` as the annotated target, which exercises the whole surface the
mission is about — status-output discoverability, annotation wiring, the guard, and the
layout — without the IAM schema.

How you learn a status field can be a source at all: the Inspector's **STATUS OUTPUTS**
block, at the bottom of every managed resource, says so in those words — *"Other
resources can wire from this object's status"* — and lists the paths. That answers M2's
first question without the user knowing the vocabulary.

Dragging onto an annotation rather than a spec field is discoverable because annotations
are not a free-text corner: the ANNOTATIONS block has the same `Val | Wire | Raw` control
the schema fields have, and its `Wire` dropdown offers the other resource's status paths
alongside the parameters:

```
"wire to…", "params.providerName", "queue (name / ID)",
"resources.queue.status.atProvider.arn", ... , "+ new XRD parameter…"
```

**Oracle met.** The binding, the guard and the layout are all correct:

```yaml
          {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
          ---
          apiVersion: v1
          kind: ServiceAccount
          metadata:
            name: {{ $xr }}-service-account
            annotations:
              {{ setResourceNameAnnotation "service-account" }}
              {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
              'eks.amazonaws.com/role-arn': {{ (index $.observed.resources "queue").resource.status.atProvider.arn | quote }}
              {{- end }}
          {{- end }}
```

The guard appeared without being asked for — both the resource-level gate CF-482 landed
and the inner per-field one. Auto-layout placed the source left of its dependent
(`queue` at x=592, `service-account` at x=833) so the wire reads left-to-right.

Emission order puts the ServiceAccount before the Queue it depends on, which is the order
they were added. Under `function-go-templating` every resource renders each pass and the
gate carries the ordering, so this is cosmetic, not a defect.

**Round-trip.** Re-importing the exported Composition returned the document intact —
resources, the annotation wire and the fields all byte-identical:

```
BEFORE: [{"n":"service-account","k":"ServiceAccount","ann":{"eks.amazonaws.com/role-arn":{"from":"resources.queue.status.atProvider.arn"}},"f":{}}, {"n":"queue","k":"Queue","ann":null,"f":{"region":{"value":"us-east-1"}}}]
AFTER : [{"n":"service-account","k":"ServiceAccount","ann":{"eks.amazonaws.com/role-arn":{"from":"resources.queue.status.atProvider.arn"}},"f":{}}, {"n":"queue","k":"Queue","ann":null,"f":{"region":{"value":"us-east-1"}}}]
```

## Candidates raised and withdrawn

Each was reproduced, then disproved. None filed.

1. **"Import is inert — it makes no API call and says nothing."** Reproduced twice with
   zero network activity. **Withdrawn: my driver's fault.** Playwright auto-dismisses
   native dialogs, so it was silently cancelling the `confirm()` above. With a dialog
   handler attached, Import works correctly and reports its losses. A reminder that a
   scripted driver's "nothing happened" needs a dialog handler before it is evidence.

2. **"The annotation Add button silently no-ops on an empty value."** Reproduced twice:
   annotations stayed `null`, the name stayed in the field, no API call. **Withdrawn:
   it does report.** A page-wide scan missed the message; scoped to `#insp` it is there
   and it is clear:

   ```
   Annotation "eks.amazonaws.com/role-arn" requires a value (or a temporary placeholder to wire)
   ```

   This is CF-136 (#21, closed) — *"The annotation form accepts an empty value, then
   fails with engine jargon and discards the key"* — working as fixed: the key is kept,
   the message is in the user's words.

3. **"`--out` claims `POST /api/generate` writes into it, but Generate wrote nothing."**
   **Withdrawn:** the UI's Generate is a preview (`"Preview only · Click Generate to
   write to …"` is on screen), and `{"write":true}` writes. Behaviour and help text agree.

## What worked

- The seeded cache (`tests/fixtures/cache`) made both missions possible offline; the
  chooser's per-starter readiness badges turn the egress limit into something a user can
  see rather than hit.
- `Wire` → `+ new XRD parameter…` collapses "declare a parameter" and "bind it" into one
  gesture. It is the single best thing in M1.
- STATUS OUTPUTS names the concept in plain words, which is the hard half of M2.
- Failures are loud where it counts: the blocked provider fetch, the empty annotation
  value, and the adopt loss report all say what happened.
- `cf gen` refuses a malformed blueprint one error at a time with the fix in the message
  (`spec.xrd.scope must be set explicitly…`, `add providerName: {type: string,
  required: true}`). Four refusals walked me to a valid document without documentation.
