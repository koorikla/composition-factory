### M2 — The status wire: IRSA · ~12 min to Generate · completed with substitution

The literal mission (IAM `Role` + `ServiceAccount`) is **blocked here**: searching


The failure is reported plainly in the SOURCES rail, nothing half-declared is left
behind, and no console error is raised. That is #68's environment, not a defect.

Substituted the cached SQS `Queue` (`status.atProvider.arn`) for the IAM Role and
ran the mission's real subject — a status field bound to an *annotation* — end to
end:

1. Dragged `Queue` and `ServiceAccount` from KINDS. Both landed first time; the
   Queue card advertises its status outputs (`name / id`, `arn`, …) on the card
   itself, which is how one learns a status field can be a source at all. Good.
2. Adding the annotation `eks.amazonaws.com/role-arn` with no value is **refused**,
   with the remedy in the message:
   `Annotation "eks.amazonaws.com/role-arn" requires a value (or a temporary
   placeholder to wire later)`. So the order of operations is placeholder-first,
   wire-second. The message says so; a user who does not read the banner will try
   twice.
3. With a placeholder in, the annotation row carries `Val | Wire | Raw` (CF-478).
   `Wire` lists every status output of every resource on the canvas, including
   `resources.queue.status.atProvider.arn`.
4. Selecting it draws the wire on the canvas and labels it
   `queue.status.atProvider.arn → service-account.annotations.eks.amazonaws.com/role-arn`.
   The guard appeared without being asked for (§3, CF-482).
5. Validate: **`validation check unavailable`** (`crossplane` CLI absent, CF-093).
   Stopped at Generate as instructed.
6. Generate wrote 4 files. Re-imported the generated Composition through the UI:
   resources, wire and parameter all came back, the annotation still a wire
   (`from: resources.queue.status.atProvider.arn`) and the source declared with
   its provider ref. Round-trip intact.

One thing worth recording for whoever scripts this next: **Generate and Import are
guarded by `window.confirm`**, which a headless driver dismisses by default. That
is correct product behaviour (both overwrite files) and cost this run several minutes
of chasing a "Generate does nothing" ghost that did not exist. Not a finding.

### M3 — Connection secret: RDS PostgreSQL · ~10 min to Generate · completed with substitution

RDS is the same story as IAM: not cached, cannot be fetched. Substituted the
cached SQS `Queue`, whose CRD carries the same `writeConnectionSecretToRef`
envelope the mission is about.

The mission asks: *is the envelope findable without knowing the word "envelope"?*
Three places were tried, in the order a person would try them:

1. **SHARED tab** — parameters and environment keys only. Nothing about
   connection secrets.
2. **XRD card inspector** — scope, parameters, pipeline. Nothing.
3. **Resource inspector** — here it is, under a heading that does not require the
   word: `CROSSPLANE ENVELOPE — Secrets, policies and metadata outside forProvider`,
   with `writeConnectionSecretToRef.name` (`string`, `REQ`, "Name of the secret.")
   and the same `Val | Wire | Raw` controls. Discoverable by scrolling.

But the panel's **own search box does not reach it** — see finding CF-484. Typing
the word a user would actually type prints `No schema field matches "secret".`
directly above the field they were looking for.

Setting the envelope value and generating produced the envelope correctly and no
literal secret anywhere in the Composition:

```yaml
          spec:
            forProvider:
              region: 'us-east-1'
            providerConfigRef:
              kind: ClusterProviderConfig
              name: {{ $spec.providerName }}
            writeConnectionSecretToRef:
              name: 'queue-conn'
```

Because the substituted resource is a queue rather than a database, the part of
M3's oracle about a *password* never becoming a literal was not exercised by the
queue. It was closed separately, on the one database path that needs no provider
download — Examples → **Cloud-Agnostic Portable Database**, loaded and generated
through the UI:

- No literal password anywhere in the generated artifacts. The composed Secret
  reads `POSTGRES_PASSWORD: {{ $env.password | quote }}`, guarded by
  `{{- if hasKey $env "password" }}`. CF-474 and CF-476 hold.
- But the value has nowhere to live. The only artifact cf emits for that key is
  `environmentconfigs/default.yaml` with `password: ""`, headed "Do not edit" —
  and the next `cf gen` rewrites an operator's value back to `""` at exit 0.
  Filed as **CF-487**.

So M3's oracle is met on the literal-password question and fails on the one after
it: the password is not in the Composition, and it is not anywhere else either.
