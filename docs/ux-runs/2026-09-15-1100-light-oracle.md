### CF-488 (#401) — closed 08:27 UTC — **verified fixed**

Independent repro, blank canvas, fresh `cf init` doc, SQS `Queue` dropped from the
palette (not the suite's fixture doc). The envelope section now reads:

```
sqs.aws.m.upbound.io/v1beta1 · 18 leaf fields · 1 required

CROSSPLANE ENVELOPE
  managementPolicies               array           placeholder: "unset — omitted from envelope"   req badges: 0
  providerConfigRef.kind           string  AUTO    placeholder: "auto: ClusterProviderConfig / $spec.providerName"
  providerConfigRef.name           string  AUTO    placeholder: "auto: ClusterProviderConfig / $spec.providerName"
  writeConnectionSecretToRef.name  string          placeholder: "unset — omitted from envelope"   req badges: 0
```

`writeConnectionSecretToRef.name` now carries no `REQ` badge and reads exactly as its
equally-optional sibling `managementPolicies` does — the contract in the issue, word for
word. The header still counts `1 required` and means `region`.

**Residue probe: does the fix over-apply?** The contract says the children must read as
optional *until the object is in use*, so a fix that simply suppressed the badge forever
would be a half-fix — a user who puts the object in use and leaves a required child unset
would get no warning. I went looking for the case that separates the two.

The seeded cache shows the envelope object has a different shape either side of the
Crossplane v2 boundary:

```
sqs.aws.m.upbound.io Queue v1beta1 scope=Namespaced children=['name']              required=['name']
sqs.aws.upbound.io   Queue v1beta1 scope=Cluster    children=['name','namespace']  required=['name','namespace']
s3.aws.m.upbound.io  Bucket v1beta1 scope=Namespaced children=['name']             required=['name']
s3.aws.upbound.io    Bucket v1beta2 scope=Cluster    children=['name','namespace'] required=['name','namespace']
```

The cluster-scoped kinds are the probe: set `namespace` and `name` must badge again. They
are **not reachable from the palette** — only `sqs.aws.m.upbound.io/v1beta1` is offered —
so through the UI the object has exactly one child and setting it is the only way to put
it in use. The over-application case therefore cannot be hit by a user today, and the
probe returns nothing to file.

Reading the fix confirms it is general rather than a special case. `isFieldEffectivelyRequired`
(`web-proto/js/regions/inspector.js:397`) walks each ancestor prefix of the path and
returns `false` only while nothing under that ancestor is set, so a sibling being set does
re-badge the rest. The raw schema flag is kept alongside it as `showReq`
(`inspector.js:548`) and still drives the optional-parameter-wire warning at `:569` and
`:573` — the split is deliberate, not a leftover. No residue.

## Mission M2 — the status wire (IRSA), stopped at Generate

**Substitution, recorded because it changes what the mission proves.** M2 wants an IAM
Role plus a ServiceAccount. `provider-aws-iam` is not in the seeded cache and the ghcr.io
blob CDN is denied here (CF-183, #68), so `cf provider add` cannot fetch it. The seeded
cache carries `provider-aws-s3` and `provider-aws-sqs` only. An SQS `Queue` — a managed
AWS resource reporting `status.atProvider.arn` — stood in for the Role; the
`ServiceAccount` is the real native kind. Every mechanic the mission is watching for
(status field as a source, dropping onto an annotation rather than a spec field, the
guard, wire readability, ordering) is exercised unchanged. What is *not* exercised is
anything specific to the IAM schema.

**Oracle: met, to the limit of the environment.** `Validate` reads unavailable (Docker
absent, CF-093), so the run stopped at Generate as the prompt requires.

Blank start → dropped `Queue` → dropped `ServiceAccount` → inspector → annotations section
→ added `eks.amazonaws.com/role-arn` → wire mode → picked
`resources.queue.status.atProvider.arn`. One `path.wire-status` rendered on the canvas; the
ServiceAccount card showed `annotations | …amazonaws.com/role-arn`. No page errors in the
whole session.

Generated Composition (`compositions/xapps.platform.example.org.yaml`), abridged:

```yaml
          {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
          ---
          apiVersion: v1
          kind: ServiceAccount
          metadata:
            name: {{ $xr }}-service-account
            annotations:
              {{ setResourceNameAnnotation "service-account" }}
              {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
              'eks.amazonaws.com/role-arn': {{ (index $.observed.resources "queue").resource.status.atProvider.arn | quote }}
              {{- end }}
          {{- end }}
```

The Queue precedes the ServiceAccount, the whole resource is gated on the ARN existing
(CF-482's fix), and the annotation is gated again inside it. `warnings: []`. The guard
appeared without being asked for, which is what the mission wanted to know.
