## Mission M2 — the status wire (IRSA)

**Goal.** An IAM Role plus a Kubernetes ServiceAccount annotated with that role's ARN, the
annotation unwritable until the Role reports it.

**Substitution, and why.** The literal mission needs `provider-aws-iam`. The seeded cache
(`tests/fixtures/cache`) holds `provider-aws-s3` and `provider-aws-sqs` only, and this
environment denies the ghcr.io blob CDN, so the IAM schema cannot be fetched here (#68).
I ran the mission's *structure* against a cached kind instead: an sqs `Queue` standing in for
the Role, and a real `ServiceAccount` (native kind) carrying
`eks.amazonaws.com/role-arn` wired to `resources.queue.status.atProvider.arn`. Every
mechanism the mission is designed to exercise — annotation-to-status binding, the guard, the
ordering — is the same one.

**Arrival.** A `#examplesOverlay` modal ("STARTER BLUEPRINTS · Choose an Example Blueprint")
is up before you touch anything, covering the canvas and intercepting pointer events. Escape
dismisses it. Reasonable onboarding for a blank start, and it is the first thing offered — not
filed.

**Finding the provider.** Searching the kinds panel for `iam` handles the miss well:

```
No kinds match search query. Add a provider in SOURCES.
MATCHING CATALOGUE PROVIDERS
provider-aws-iam      ghcr.io/crossplane-contrib/provider-aws-iam:v2.7.0     [Add]
provider-gcp-iam      ghcr.io/crossplane-contrib/provider-gcp-iam:v3.0.0     [Add]
```

The empty state names the next action and the catalogue offers the right package first.

One observation, not filed. Searching `role` — the word a user arriving at *this* mission is
most likely to type — returns only the RBAC kinds:

```
RBAC.AUTHORIZATION.K8S.IO   Role (1 req)   RoleBinding (5 req)
```

No catalogue row, no hint that `provider-aws-iam` exists and carries the `Role` this mission
wants. Catalogue search matches provider names and descriptions, not the kind names inside a
package, so `role` cannot reach `provider-aws-iam`. Returning the k8s `Role` for `role` is
correct behaviour, and indexing kind names is a feature wish rather than a defect
(backlog-authoring §2), so this is recorded here rather than filed. It is worth a driver's
attention as a discovery gap: the naive path to an IAM Role ends on the wrong kind, silently.

**Building it.** Drag from the kinds panel onto the canvas works on first try for both kinds;
the dropped resources are named `queue` and `service-account` automatically.

The annotation path — the surface CF-478 (#387) opened — is discoverable. The Inspector shows
an `ANNOTATIONS` section with an `Add` button; the new row's value input is labelled
`value (or placeholder to wire)`, which is the only place the canvas tells you a value can be
something other than a literal. Committing the row (key plus value, Enter) gives the committed
row a `Wire` button, and `Wire` opens a dropdown listing the status paths available:

```
wire to…
params.providerName
queue (name / ID)
resources.queue.status.atProvider.arn
resources.queue.status.atProvider.deduplicationScope
resources.queue.status.atProvider.id
resources.queue.status.atProvider.url
...
+ new XRD parameter…
```

Selecting `resources.queue.status.atProvider.arn` rewrites the annotation from a literal to a
wire in the document:

```json
{
 "name": "service-account",
 "kind": "ServiceAccount",
 "ann": { "eks.amazonaws.com/role-arn": { "from": "resources.queue.status.atProvider.arn" } }
}
```

A row committed with a key but no value is dropped instead of kept as an empty annotation —
correct, and it does not look like a loss once you notice the value input is what commits it.

**Generate.** Green, no console errors at any point in the mission. The emitted ServiceAccount:

```
          {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
          ---
          apiVersion: v1
          kind: ServiceAccount
          metadata:
            name: {{ $xr }}-service-account
            annotations:
              {{ setResourceNameAnnotation "service-account" }}
              {{- if hasKey (dig "resources" "queue" "resource" "status" "atProvider" dict $.observed) "arn" }}
              'eks.amazonaws.com/role-arn': {{ (index $.observed.resources "queue").resource.status.atProvider.arn | quote }}
              {{- end }}
          {{- end }}
```

**Oracle — met.** The annotation is bound to the source's `status.atProvider.arn`; the binding
is guarded, at the resource level as well as the line level; and the `queue` template precedes
the `service-account` template, so the dependency reads in document order. The guard appeared
without being asked for. This is CF-482's fix arriving end-to-end through the UI, on a path
built entirely from the canvas — a useful confirmation that the emit-side fix and the CF-478
annotation surface meet correctly.

Validate not attempted: Docker is absent here, so it reads "unavailable" (CF-093), and the run
parameters stop the mission at Generate.
