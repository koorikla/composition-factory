### CF-476 — master password out of the XR spec

The contract was that the Portable Database starter must obtain its master password from
somewhere other than the composite's own `spec`. `f4602ff` moves it to an EnvironmentConfig key.
Regenerating the starter from `internal/examples/cloud-database.cf.yaml`:

```
=== required ===
44:            required: [providerName]
=== composition PG password ===
 9:    factory.crossplane.io/environment-keys: '{"password":{"type":"string","description":"Master password for PostgreSQL."}}'
48:          {{- if or (hasKey $spec "dbName") (hasKey $env "password") (hasKey $spec "username") }}
53:            {{- if hasKey $env "password" }}
54:            POSTGRES_PASSWORD: {{ $env.password | quote }}
```

`password` is gone from the XRD's properties and from its `required` list; the Composition reads
`$env.password` under a `hasKey` guard. The emitted EnvironmentConfig carries no literal:

```yaml
data:
  password: ""
```

Two consecutive `cf gen` runs into different directories were byte-identical (`diff -r` clean),
so this is not a one-run artifact. Both clauses of CF-474's contract now hold.

### M1 — first contact: an S3 bucket, from nothing · **oracle met**, ~14 min to Generate

Blank start, no blueprint file on disk.

**Arrival.** The canvas opens with the KINDS palette populated and the XRD card at top-left. On a
genuinely blank document the *Starter Blueprints* chooser opens over the canvas and intercepts
pointer events on it until dismissed — visible here only because a scripted drag (which
dispatches DOM events directly) placed cards *through* the open modal and the subsequent real
click was blocked by `#examplesOverlay .example-tags`. For a human this is one Escape; noting it
as arrival friction, not a defect.

**Search.** `s3` and `bucket` both surface `Bucket` first — the word a user knows works. `storage`
finds no local kind but offers the catalogue instead of a dead end, which is the right answer:

```
search "storage" -> 0 rows | EMPTY-STATE: "No kinds match search query. Add a provider in SOURCES.
MATCHING CATALOGUE PROVIDERS
provider-azure-storage
ghcr.io/crossplane-contrib/provider-azure-storage:v2.7.0
Add …"
```

`encrypted` returns the bare form of that message with no catalogue rows — accurate, since no
provider is named "encrypted", but it is the one search that ends in nothing.

**Drop.** Dragging `Bucket` onto the canvas did the right thing without being asked: it registered
the provider as a source and scaffolded the required field.

```
resources after drop: [{"name":"bucket","kind":"Bucket","provider":"ghcr.io/crossplane-contrib/provider-aws-s3:v2.7.0","fields":["region"]}]
spec.sources after drop: [{"provider":"ghcr.io/crossplane-contrib/provider-aws-s3:v2.7.0"}]
```

**Parameterise and wire.** `Wire` → `+ new XRD parameter…` → `region` → Add produced both the
parameter and the binding in one gesture (and, per §2, closed cleanly).

**Generate.** Four files written. The oracle is met — the XRD declares the parameter with its
type, and the Composition takes `region` from the XR:

```yaml
              region:
                type: string
            required: [providerName]
```
```
              {{- if hasKey $spec "region" }}
              region: {{ $spec.region | quote }}
              {{- end }}
```

Validate reads `validation check unavailable` / `crossplane CLI not found on PATH` — CF-093, this
environment, not filed. The mission therefore stops at Generate by design.

Two things cost time and are worth recording without being filed. `Generate` goes through
`window.confirm` (`output.js:915`), which a headless driver auto-dismisses — so the primary
action appeared to do nothing at all (no request, no toast, no files) until the dialog was
accepted. That is a harness artifact, **not** a product defect, and it is written down here
because it looked exactly like a P0 for about ten minutes. Separately, the `region` parameter
created through the inline form lands with no `description`; the user never typed one, so this is
noted rather than filed.

### M2 — the status wire: IRSA · **oracle not reachable through the UI** → CF-478

Blank start. The mission's own subject, `provider-aws-iam`, is in the catalogue but cannot be
fetched here — the known egress wall (#68):

```
{"error":"ghcr.io/crossplane-contrib/provider-aws-iam:v2.7.0: read image config: Get \"https://pkg-containers.githubusercontent.com/ghcrblobs20/blobs/sha256:a7f6…\": Forbidden"}
```

That is exactly where the missing schemas stop the mission, and it is not filed. The status-wire
*mechanics* the mission exists to measure were then exercised with the cached SQS `Queue`
(`status.atProvider.arn`) as the source and a native `ServiceAccount` as the target — the same
shape as IRSA, same annotation, same guard question.

**How you learn a status field can be a source:** well. The canvas draws status ports on the
source card and each one says so in its tooltip —
`queue.status.atProvider.arn (status output — other objects can wire from this)`.

**Whether dragging onto an annotation is discoverable:** it is not, because it is not possible.
Adding `eks.amazonaws.com/role-arn` through the inspector's Annotations form produces a row with
a delete button and nothing else — no `Val|Wire|Raw`, no dropdown — and dragging the ARN port
onto it leaves the document unchanged. The form's own placeholder says *"value (or placeholder to
wire)"*. Filed as **CF-478 (#387)**, P2, with the DOM dump and the drag result.

The empty-value path, by contrast, is exemplary and is *not* a finding — it refuses loudly and
tells you why:

```
Annotation "eks.amazonaws.com/role-arn" requires a value (or a temporary placeholder to wire later)
```

So the guard question and the readability question could not be reached: there is no wire to
guard or to read. The engine and the renderer both support the binding —
`tests/slice37-annotation-wires.spec.js` proves the wire *renders* — but that spec seeds it
through `PUT /api/blueprint` rather than authoring it in the UI, which is why the gap is not
caught by a gate.
